# SarSim0 configuration and data flow

SarSim0 supplies the synthetic training stream and fixed held-out evaluation
sets used in this repository. Its data-generation package is pinned in
`pyproject.toml` and `uv.lock`; the committed experiment setup is also recorded
in run manifests.

## Configuration block

Training and generation receive a nested `sarsim:` block. [SARSIM_DEFAULTS](../src/sarsim_fm/data/sim.py)
applies these repository-level defaults first:

| Key | Default | Meaning |
|---|---:|---|
| `series_length` | 6000 | Total-series length setting passed to `SarSimConfig` |
| `burn_in` | 200 | Package burn-in/warm-up length passed to `SarSimConfig` |
| `multivariate_prob` | 0.0 | Probability of multivariate output; fixed at univariate |
| `with_covariates_prob` | 0.0 | Probability of covariate-bearing output; fixed at none |
| `pad_max` | 0 | Maximum padding; fixed at no padding |

Other keys are passed to `SarSimConfig`. Range fields such as `s_range` and
the tuple-based fields are converted to the types expected by the installed
SarSim0 package. `seasonality_pairs` is converted to a list of integer pairs.
For example:

```yaml
data:
  context_length: 512
  prediction_length: 18
  batch_size: 8
  seed: 42
  sarsim:
    s_range: [60, 120]
    seasonality_pairs: [[0, 96], [0, 120], [96, 7], [7, 96]]
```

The repository merges `data.sarsim` over the defaults. Unmentioned
`SarSimConfig` fields use the pinned package defaults. The keys documented
above are repository experiment defaults, not additions defined in this repo;
they are forwarded through `sarsim_config(...)`.

## Training stream

`sfm train` constructs `SarSim0StreamingDataset` with an infinite stream.
When worker processes are enabled, each worker is seeded from
`data.seed + worker_index`; the base config uses `num_workers: 0`.
SarSim0 generates the context and target arrays, while the repository controls
the context length, prediction length, batch size, seed, and `sarsim:` override.

The training stream is univariate and has no covariates or padding. This is the
setup used for the original Chronos-2 experiments. `batch_size` is a
micro-batch size; a SarSim0 batch itself can contain repeated parameter sets,
and the data module's held-out code documents this limitation.

## Fixed held-out sets

`configs/data/sim-heldout.yaml` is the fixed-evaluation configuration:

The example file `configs/data/sarsim0-example.yaml` contains 100 series per
split for a small demonstration. The repository's fixed `sim-heldout.yaml`
configuration uses 2,000 series per split.

- `defaults.n_series`, context, horizon and season length are inherited by every
  split.
- Each split has an independent seed.
- Seeds differ from training seeds; for example, training defaults start at 42
  and worker `i` uses `42 + i`.
- Each held-out series is generated by a separate generator call. This avoids
  using only a few distinct SARIMA processes in a large batch.

Build the sets:

```bash
uv run sfm make-sim
uv run sfm make-sim --config configs/data/sarsim0-example.yaml --only sarsim0_iid_example
uv run sfm make-sim --set defaults.n_series=20 --only sim_iid
```

The output is a Parquet table with `item_id`, `context`, `target`, and
`season_length`, plus a JSON manifest containing the resolved split
specification and seed. The same format is consumed for MASE, sMAPE, SQL, WQL,
and coverage metrics.

## IID and season OOD examples

The default configuration has two held-out splits:

| Split | Distribution | Purpose |
|---|---|---|
| `sim_iid` | Same training-style Table 9 defaults, seed 1000003 | Same-distribution synthetic performance |
| `sim_ood_season` | `s_range` 60–120 and listed seasonal pairs | Seasonal out-of-distribution behavior |

The comments in the config explain why 60–120 is outside the ordinary training
period range: the plain SARIMA distribution selects `s` from 0–52, while the
Table 9 pairs cover shorter or lower pairs.

## Synthetic anomalies

Synthetic anomaly splits use a separate workflow:

```bash
uv run sfm make-anomaly-sim configs/data/sim-anomaly-dev.yaml
uv run sfm make-anomaly-sim configs/data/sim-anomaly-test.yaml
```

These configs combine SarSim0 clean-series generation with the repository's
injection code. The generated Parquet rows contain the clean series, injected
series, label interval, kind, severity and seed. Injection kinds and label
half-open semantics are implemented in `src/sarsim_fm/data/anomaly_injection.py`.
Normal splits set `anomaly_kind` to `normal` and have no label interval.

## Reproducibility and caveats

- Record the run config, package versions, Git SHA, and SarSim0 commit.
- Keep the YAML and every `--set` override with a unique run name.
- Changing a seed or SarSim0 override changes the data and makes result
  comparisons non-equivalent.
- The pinned package commit is `71306403`, but strict reproduction should also
  record Hugging Face model revisions and external M4 checkout commits.
- Package-series data can reach ±1e6 or have all-zero contexts. Synthetic
  anomaly generation rejects such clean series and retries; held-out and
  training distributions otherwise expose these edge cases rather than silently
  removing them.
- Synthetic seasonal periods are an approximate configuration of seasonality,
  not a statement about hourly wall-clock time in DERConnect.
